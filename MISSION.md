# Mission: Practical Rust for Systems Work and TUI Applications

## Why
You want Rust to become a natural extension of your existing systems-programming instincts, not a language you merely tolerate at work. You need to become productive in a Rust-based company codebase, and you also want to ship a complete TUI application you would actually use and feel proud of.

## Success looks like
- You can read unfamiliar production Rust and explain ownership, trait, closure, concurrency, and error-handling choices without constantly second-guessing yourself.
- You can make meaningful contributions to your company's Rust codebase using idiomatic, test-backed changes.
- You ship a complete, non-toy ZMQ topic-monitor TUI application with clean state management, tests around core behavior, and enough polish that you would keep using it.
- Rust starts to feel like a safer way to express your Linux/Android systems background rather than a fight with the compiler.

## Constraints
- Current level: beginner-to-intermediate Rust; The Rust Programming Language has been read once, and Rustlings + Rustify are complete.
- Strong prior background: PhD in Computer Science; years of C-based performance, power, and thermal profiling/optimization at Linux kernel and Android platform level; experience with NNStreamer, device drivers, and Android MLOps.
- Weakest current areas: closures and concurrency, especially translating C-style systems thinking into idiomatic Rust designs.
- Preferred learning mode: project-first, concept-reinforced, TDD-driven; introduce concepts in the context of the project, then review, quiz, and implement test-first.
- Depth preference: do not avoid hard topics. If unsafe, lifetimes, macros, async, or advanced trait design arise naturally, tackle them directly.

## Out of scope
- Theory-only Rust study detached from a concrete artifact.
- Repeating beginner material already covered by Rustlings/Rustify unless it blocks project progress.
- Toy examples that do not transfer to production Rust or the TUI application.
