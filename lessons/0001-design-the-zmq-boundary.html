Design the ZMQ Boundary

First Rust move: make the real socket somebody else's problem.

The tangible win

By the end of this lesson, you will have the first testable seam of the TUI project: a domain model that can accept topic messages without needing a real ZMQ socket.

This matters because ZeroMQ is a messaging system with real timing and delivery behavior, while early Rust learning needs deterministic feedback. We will put ZMQ behind a boundary, then test the core with fake messages.

Concept: isolate effects from state transitions

In C, you may be tempted to start with the socket loop: connect, subscribe, receive, parse, update globals, draw UI. In Rust, that quickly tangles ownership, lifetimes, blocking IO, and UI mutation.

The Rust-native shape is cleaner:

MessageSource --> RawMessage --> Parser --> DomainEvent --> AppState --> View

The core idea is: make state transitions pure and testable before attaching real IO. Ratatui rendering can later read AppState, and a ZMQ adapter can later implement MessageSource. See the architecture reference.

Why this teaches Rust

  • Ownership: RawMessage owns topic and payload bytes, so the UI never borrows from a socket buffer that has already moved on.
  • Traits: MessageSource lets tests use a fake source while production uses the zmq crate.
  • Concurrency: later, ingestion and rendering can be separate loops connected by channels, instead of shared mutable state.
  • TDD: tests can verify topic counts, parse errors, and state updates without timing-sensitive networking.

Quick retrieval quiz

Answer from memory first. Then open each answer.

1. What should the first tests target: real ZMQ sockets, Ratatui drawing, or state transitions?

State transitions. The first reliable tests should target parsing and AppState::apply, because they are deterministic and central to the application.

2. Why should RawMessage own its topic and payload?

Because messages cross boundaries. Owning the data avoids borrowed socket-buffer lifetimes leaking into parsing, state, or rendering code.

3. What is the purpose of a MessageSource trait?

It hides where messages come from. Tests can use fake messages; production can use a ZMQ adapter; replay tools can use a file source.

Setup

cargo new zmq-topic-monitor
cd zmq-topic-monitor

Red: write tests first

In src/lib.rs, write tests for this behavior:

  1. A new AppState has zero total messages.
  2. Applying a RawMessage with topic "thermal.cpu" increments total messages to one.
  3. Applying two messages with different topics records a per-topic count for each.

Green: implement the minimum

Implement only enough to pass:
