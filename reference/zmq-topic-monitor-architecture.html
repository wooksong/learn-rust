ZMQ Topic Monitor Architecture

A compact reference for the Rust TUI project.

Boundary-first architecture

MessageSource --> RawMessage --> Parser --> DomainEvent --> AppState --> Ratatui View

The key design move is to keep ZMQ at the edge. The core application should not know whether messages came from libzmq, a test fixture, a file replay, or an in-process fake.

Core types

  • RawMessage: bytes plus topic metadata exactly as received.
  • DomainEvent: validated, parsed information the app understands.
  • ParseError: a recoverable failure displayed in the UI instead of crashing ingestion.
  • AppState: deterministic state updated by applying events.
  • MessageSource: trait hiding fake, replay, blocking ZMQ, or async ZMQ sources.

Testing rule

Tests should target Parser and AppState::apply before real networking. A fake source should produce deterministic RawMessage values so failures explain Rust design mistakes, not socket timing.

Concurrency rule

One loop owns ingestion; one loop owns UI state/rendering. They communicate through channels. Avoid shared mutable state until there is a measured reason to need it.
